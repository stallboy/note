## 第 0 章 根命题：响应性哲学的分叉

市面上大多数 Vue/React 对比是这样开头的：「`v-if` 对应 `&&`，`ref` 对应 `useState`……」——这是**招式对比**，停留在语法映射，结论永远是「各有千秋」。

深刻对比必须从那个让所有差异成为必然的根本问题开始：

> **UI 如何随着状态变化而更新？**

Vue 和 React 对这个问题给出了**两套相反的哲学答案**。把它们摆在一起：

| | **React** | **Vue** |
|---|---|---|
| 状态观 | **不可变快照**（immutable snapshot） | **可变响应源**（mutable reactive signal） |
| 变化的本质 | 状态变了 → **重新调用整个组件函数** | 状态变了 → **精准触发依赖它的副作用** |
| 如何找到要更新的 DOM | 运行时 **diff**（Virtual DOM reconciliation） | **编译期优化 + 运行时依赖追踪**，多数情况无需 diff |
| 核心隐喻 | UI 是 `f(state)` 的**纯函数投影** | UI 是一张**订阅网络的物化** |

**这张表是整篇文章的引力中心。** 后面每一章，我都会问同一个问题：「这个差异，是不是上面这个根命题的必然推论？」如果是，它就是本质差异；如果只是历史偶然或口味问题，就归到次要差异，不喧宾夺主。

读完全文你会发现：hooks 为什么有那么多「规则」、为什么 React 有闭包陷阱、为什么 Vue 的状态可以脱离组件存在、为什么两个框架在 2026 年都搞了「Compiler」却解决不同的问题……全部都能回溯到这一张表。

记住它，我们开始。

## 第 1 章 第一性原理：两种世界观

### React：把「时间」从状态里拿掉

React 的核心信条是：**UI = f(state)**。

这里的 `state` 是某个**时刻的快照**——它不是「正在变化的东西」，而是「此刻世界是什么样」。`f` 是纯函数：**同样的 state 永远渲染出同样的 UI**。

要让屏幕跟着变怎么办？React 的答案是：**不要去「修改」状态，而是产出一个新的 state，让 f 重新跑一遍。**

```tsx
// React：状态是「替换」，不是「修改」
const [count, setCount] = useState(0)
setCount(count + 1)   // 产出一个新值 1，而不是把 0 改成 1
```

这种**不可变（immutable）**模型带来一个巨大的好处：**可预测性**。因为状态从不被原地修改，你永远可以信任「当前的 state」就是当前 UI 的唯一来源；时间旅行调试、memoization、并发渲染（Concurrent）都建立在这个假设上。

代价是什么？React **不知道到底「哪里」变了**。它只知道「state 变了，于是整棵组件子树都要重新求值」。至于 DOM 上具体哪个节点要改，React 靠**重新生成虚拟 DOM 树，然后 diff** 来推断（详见第 3 章）。

> 给初中级的一句话：在 React 里，「修改数据」是被禁止的思考方式。你永远在说「给定新的 state，UI 应该长什么样」，而不是「把这个数据改一下，让 UI 跟着改」。

### Vue：状态是「活的」，它自己知道谁依赖它

Vue 走了完全相反的路：**状态本身就是响应式的**——它是一个「活」的对象，会自动追踪「谁读了我」，并在被改变时通知「读过我的那些人」。

```vue
<!-- Vue：状态是「活的」，可以直接改 -->
<script setup>
import { ref } from 'vue'
const count = ref(0)
function inc() { count.value++ }   // 直接改，UI 自动更新
}
</script>
<template>
  <button @click="inc">{{ count }}</button>
</template>
```

这里没有「重新跑一遍组件函数」这回事。`count` 变了，Vue 的响应式系统精准地知道：模板里那个按钮的文本依赖了 `count`，于是**只更新那一个文本节点**。不需要 diff 整棵树。

代价是什么？响应式有运行时开销（要拦截读写、维护依赖关系），并且开发者要理解「什么操作会被追踪、什么不会」（比如解构会丢掉响应性）。

> 给初中级的一句话：在 Vue 里，你声明「这个数据是响应式的」，然后就可以像写普通 JS 一样直接改它。框架替你盯着「谁依赖它、变了通知谁」。

### 分叉点

两套世界观都自洽，但它们把**复杂性**放在了不同的地方：

- **React** 把复杂性交给**运行时调度**（重算很贵 → 需要 Fiber、Concurrent、diff 优化）。
- **Vue** 把复杂性交给**响应式系统 + 编译器**（写起来直观 → 需要 Proxy 拦截、依赖收集、编译期分析）。

这个「复杂性放在哪里」的主题，会在第 3 章和第 6 章反复出现。

## 第 2 章 响应性机制的本质

这是两套体系最硬核的技术差异，也是性能模型和心智模型的根源。

### React：隐式、粗粒度的依赖

当你在 React 里 `setState`，发生的事情是：

1. 给这个组件**打个脏标记**；
2. 调度一次**重新渲染**——整个组件函数从头到尾再跑一遍，产出新的虚拟 DOM；
3. 把新虚拟 DOM 和旧的做 **diff**，找出最小变更集；
4. 把变更提交到真实 DOM。

注意第 1、2 步：React 的更新粒度是**组件级**的。哪怕 state 里只有一个字段变了，**整个组件函数**（以及它用到的所有子组件，除非 memo 了）都要重跑。

更关键的是——**React 不知道你的副作用依赖了哪些状态**。`useEffect` 的第二个参数（依赖数组）要你**手写**：

```tsx
// React：依赖要你手动声明，写错就 bug
useEffect(() => {
  document.title = `Hello ${name}`
}, [name])   // 漏了 name？要么不更新，要么 lint 报错
```

这是 React 响应性最痛的点：**依赖关系是人维护的，不是系统自动发现的。** 漏写依赖、依赖数组里放对象/函数导致无限循环——这些坑每个 React 开发者都踩过。

### Vue：显式收集、细粒度的依赖

Vue 的响应式基于 **Proxy 拦截读写**（Vue 3；Vue 2 用的是 `Object.defineProperty`）。原理可以简化为：

- **读**一个响应式数据时（在某个「副作用」effect 里，比如渲染、computed、watch），系统记下「这个 effect 依赖了这个数据」；
- **写**这个数据时，系统找出所有依赖它的 effect，**只通知它们**重新执行。

```js
// Vue 响应式原理（伪代码）
const state = reactive({ count: 0 })
effect(() => {
  // 这个 effect 里「读了」state.count → 自动建立依赖
  console.log(state.count)
})
state.count = 1   // 精准触发上面的 effect，打印 1
```

依赖收集是**自动**的、**细粒度**的（精确到对象的**某个属性**，不是整个对象，更不是整个组件）。

```vue
<!-- Vue：依赖自动追踪，无需手写 -->
<script setup>
import { ref, watch } from 'vue'
const name = ref('World')
watch(() => {
  document.title = `Hello ${name.value}`   // 自动追踪 name，不用写依赖数组
})
}
</script>
```

### 闭包陷阱：根命题的必然副作用

理解了上面的机制，「闭包陷阱」就不再是玄学了。

React 每次渲染都是**新的函数调用、新的闭包**。事件处理器、setTimeout 回调里捕获的 `count`，是**那一次渲染时的旧值**：

```tsx
// React 经典坑
const [count, setCount] = useState(0)
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1)   // count 永远是 0！闭包捕获了首次渲染的 count
  }, 1000)
  return () => clearInterval(id)
}, [])
```

这不是 React 的 bug，而是**不可变快照模型的必然结果**：每次渲染的 `count` 就是一个快照值，闭包自然捕获快照。解法（函数式更新 `setCount(c => c + 1)`、把 count 加进依赖、用 ref）都是对这个模型的「修补」。

Vue 几乎没有这个问题，因为 `ref` 是一个**持久的引用对象**，`count.value` 永远读到最新值——这正是「可变响应源」模型的好处。

> **回扣根命题**：闭包陷阱 vs 自动依赖，本质就是「快照 + 手动依赖」与「引用 + 自动依赖」两种状态观在体验上的投影。

## 第 3 章 渲染管线：复杂性放在哪里

从「state 变了」到「屏幕像素变了」，两个框架走的管线截然不同。

### React：Virtual DOM + Fiber + Concurrent

React 的更新流程要处理一个根本难题：**因为我必须重算整棵子树，万一一棵树特别大，会不会卡顿？**

React 的解法是 **Fiber 架构**——把渲染工作拆成一个个小单元（fiber），做成**可中断、可恢复**的链表结构。由此衍生出 **Concurrent（并发）渲染**：

- **时间分片**：把一次大渲染拆成多帧，每帧做一点，保持页面响应；
- **优先级调度**：用户输入的更新可以「插队」打断低优先级更新；
- **Suspense / use() / transitions**：都是建立在「渲染可中断」之上的能力。

> 给初中级：你可以粗略地把 Concurrent 理解成「React 能在渲染到一半时暂停，先去处理更紧急的事，再回来继续」。这在 React 18 之后是默认开启的能力。

**注意这里的因果**：Concurrent 不是 React 的炫技，而是**对「必须重算」这个根本代价的补救**。因为重算贵，所以才需要分片和优先级。Vue 不需要 Concurrent 来解决同样的卡顿问题，因为它压根不重算——它精准触发，天生就只做最少的工作。

### Vue：编译期优化 + 运行时响应式

Vue 的策略完全不同：**编译器替你把模板分析透，运行时只做最少的事。**

Vue 3 的编译器做了三件关键优化：

1. **静态提升（Static Hoisting）**：模板里纯静态的节点（没有动态绑定的）被提到 render 函数外，**只创建一次**，后续复用。
2. **PatchFlag**：编译器给每个动态节点打标记，告诉运行时「这个节点只有 class 是动态的，text/style 都不会变」。于是 diff 时**只比动态部分**，跳过其余。
3. **Block Tree**：把 diff 的范围从「整棵树」缩小到「一个 block 内的动态子节点集合」，进一步砍掉遍历成本。

结果是：Vue 的运行时几乎不需要做传统意义的「diff」。响应式系统精准通知「哪个 effect 脏了」，effect 重新执行时，凭借 PatchFlag 只比对真正会变的那一点。

> 给初中级：React 的 diff 是「通用 diff」——它假设什么都可能变，于是什么都比。Vue 的 diff 是「编译器裁剪过的 diff」——编译器在构建时就告诉你哪里会变，运行时只看那里。

### 分叉点

把第 1、3 章合起来看，那条贯穿主线浮现了：

> **React 把复杂性放进运行时（Fiber 调度器、Concurrent、通用 diff）；Vue 把复杂性放进编译期（静态分析、PatchFlag、Block Tree）和响应式系统。**

这条主线会在第 6 章（编译 vs 运行时）和第 9 章（两个 Compiler）继续主导叙事。

## 第 4 章 组件模型与心智模型

「心智模型」（mental model）是指：**你写组件时，脑子里在想什么。** 这直接决定日常生产力，也是「开发体验」的内核。

### Thinking in React：UI 是状态的照片

React 官方有一篇名文《Thinking in React》，它教你的思维方式是：

1. 把 UI 拆成组件树；
2. 找出「最小可变状态」；
3. 决定状态住在哪个组件，如何下传。

关键是第 3 步背后的心法——**你不写「如何变化」，你写「给定这个 state，UI 长什么样」**。变化是 setState 触发重渲染后「自然涌现」的。你思考的单位是「某一时刻的 UI 快照」。

### Vue SFC + setup：声明响应关系

Vue 的单文件组件（SFC）让你把同一个组件的模板、逻辑、样式放在一起，心智更接近「声明这张界面依赖哪些数据、数据怎么流动」：

```vue
<script setup>
import { ref, computed } from 'vue'
const todos = ref([])
const newTodo = ref('')
const remaining = computed(() => todos.value.filter(t => !t.done).length)
function add() {
  todos.value.push({ text: newTodo.value, done: false })
  newTodo.value = ''
}
}
</script>
<template>
  <form @submit.prevent="add">
    <input v-model="newTodo" />
    <span>剩余 {{ remaining }} 项</span>
  </form>
</template>
```

`setup` 只在组件初始化时**执行一次**，之后的状态都装在 `ref`/`reactive` 这个「响应式容器」里持续存在。

### Hooks vs Composition API：表面像，本质不同

这是最容易被误读的点。Vue 的 Composition API 看起来和 React Hooks 很像（都是 `useXxx` 风格、都是函数式组合），但**底层机制完全不同**：

| | React Hooks | Vue Composition API |
|---|---|---|
| 调用时机 | **每次渲染都重新调用** | **只在初始化时调用一次** |
| 状态存哪 | 靠**调用顺序**在 fiber 上挂载的链表 | 装在 `ref`/`reactive` 这个**响应式对象**里 |
| 能否条件调用 | **不能**（顺序错乱会崩） | 能（就是普通函数调用） |
| 为什么有这个限制 | React 没有细粒度响应式，只能靠顺序维持状态对应关系 | Vue 有响应式系统，状态独立存在，不依赖调用顺序 |

**Hooks 必须在顶层、不能放在 if/循环里**——这条著名的「Hooks 规则」，本质是 React 没有细粒度响应式的**补救措施**。它靠「第 N 次调用 hook」对应「状态数组第 N 项」来维持状态，所以调用顺序不能变。

Vue 的 `setup` 只跑一次，状态装在 ref 里持续存在，自然没有这个限制。这也是为什么 Vue 官方说「Composition API 吸收了 hooks 的组合优点，但避开了它的陷阱」。

> **回扣根命题**：Hooks 的种种「怪规则」和闭包陷阱，根因都是同一个——**React 没有细粒度响应式，状态靠「函数反复重跑 + 顺序链表」维持**。Vue 有响应式，setup 只跑一次，于是没有这些坑。

## 第 5 章 状态管理：渲染问题还是数据问题

中大型项目里，状态架构是成败关键。两个框架在这层的差异，依然是根命题的投影。

### React：状态是「渲染的输入」

在 React 里，状态默认是**组件私有的**。要跨组件共享，标准做法是 **lifting state up**（提升到共同祖先）+ props 一层层下传。层数一深就是 **props drilling**。

为了治 props drilling，React 生态演化出了一长串方案：

- **Context**：官方内置，但**任何一个 Context 值变了，所有消费者都会重渲染**（粗粒度，根命题决定）；
- **Redux**：最早的「正经」方案，但样板代码重；
- **Zustand / Jotai / Recoil / Valtio**：各种更轻量的库，思路各异。

注意：**这些都不是 React 官方提供的**。React 把状态管理视为「社区问题」，自己只给 `useState`/`useReducer`/`Context` 这几块积木。

而且——React 把状态管理当作**渲染问题**：状态是渲染的输入，所以「共享状态」天然要和「怎么避免无谓重渲染」绑在一起讨论（`useSelector`、`useSyncExternalStore`、各种 selector 优化）。

### Vue：响应式是独立于渲染的基础设施

Vue 的响应式系统是**全局的基础设施**，不绑定组件。你可以在任何 `.js`/`.ts` 文件里定义一个响应式对象：

```js
// store.js —— 普通模块，导出一个响应式对象
import { reactive, computed } from 'vue'
export const store = reactive({
  todos: [],
  get remaining() { return this.todos.filter(t => !t.done).length }
})
```

任何组件 `import` 它就能用，且**自动是响应式的**——因为响应性是数据的属性，不是组件的属性。

**Pinia**（Vue 官方推荐的状态库）就是建在这个事实之上的：它本质是「带 devtools 和类型支持的反应式 store 模式」，比 Redux 轻得多。

> **回扣根命题**：React 把状态当「渲染输入」，所以状态共享总伴随着渲染优化问题；Vue 把响应式当「独立于渲染的数据层」，状态共享就是「到处 import 一个响应式对象」那么自然。这就是「响应式该不该是全局基础设施」这个分歧的体现。

## 第 6 章 编译 vs 运行时

这一章是第 3 章「复杂性放在哪」的延伸，也是第 9 章（两个 Compiler）的伏笔。

### React：JSX 就是函数调用

React 的 JSX 在编译后就是普通的函数调用：

```jsx
// 这两行等价
const el = <div className="x">{count}</div>
const el = jsx('div', { className: 'x', children: count })
```

编译器（Babel/SWC）**只做语法转换**，不做任何「理解模板结构」的优化。运行时拿到的是一个普通的函数调用结果，对「哪些节点是静态的、哪些绑定会变」**一无所知**——这正是为什么 React 必须做「通用 diff」（第 3 章）。

历史上，React 刻意保持「JSX 是纯运行时」的纯粹性。这带来了灵活性（JSX 里可以随便写 JS），代价是**放弃了编译期优化**。

### Vue：SFC 是编译产物，编译器理解模板

Vue 的 `<template>` 是一个**会被分析的字符串**。Vue 的编译器能看出哪些是静态节点、哪些指令会动态绑定，于是能做静态提升、PatchFlag、Block Tree（第 3 章）。

换句话说：**Vue 拿到了 React 主动放弃的那份「编译期信息」，并用它换来了运行时的轻量。**

这是两种工程哲学的直接对立：

- React：「运行时纯粹、灵活，优化靠运行时调度。」
- Vue：「让编译器帮忙，运行时做更少。」

> 伏笔：这个对立在 2026 年出现了微妙变化——React 也开始有「Compiler」了。但第 9 章会澄清：React Compiler 和 Vue 的编译器，解决的是**不同的问题**，别被名字骗了。

## 第 7 章 类型系统

TypeScript 已是前端标配，类型 DX（开发体验）是日常真实体验。

### React：成熟，但「贴在运行时之上」

React 的类型来自 `@types/react`（历史上由社区维护，现逐步官方化）。函数组件的 props 类型、JSX 的类型推断、hooks 的类型推导，都很成熟强大。

但它的类型本质是「**在运行时之上做标注**」——类型系统是对已存在的 JS 运行时行为的描述，运行时不感知类型。

### Vue 3：用 TS 重写，编译器打通类型

Vue 3 的核心用 TypeScript 重写。配合 **Volar**（Vue 官方语言服务，VS Code 插件），模板表达式也能获得类型检查和自动补全。

最体现「编译器打通类型」的是 `defineProps` 宏：

```vue
<script setup lang="ts">
// 写一个类型，编译器自动生成对应的运行时 props 声明
const props = defineProps<{
  title: string
  count?: number
}>()
}
</script>
```

你只写一次类型，编译器既用它做类型检查，又从它**生成运行时的 props 校验声明**。这种「一份类型，编译期 + 运行时都用」的体验，是 Vue「编译器深度参与」哲学的延续。

> **回扣第 6 章**：React 的类型「贴在运行时上」，Vue 的类型「被编译器吃进去」。差异的根还是那个：**编译器参与多深。**

## 第 8 章 生态与治理：两种开源哲学

这一层不是技术，而是**治理**，但它深刻影响团队选型和长期维护成本。

### React：Meta 背景 + 社区驱动 + Unopinionated

React 由 Meta（Facebook）开源，但官方只提供**核心库**。路由用谁？状态用谁？构建用谁？测试用谁？**官方不给你答案**，全靠社区：

- 路由：React Router（社区，Remix 团队）
- 状态：无官方，Redux/Zustand/Jotai 各据一方
- 构建：Create React App 已实质弃用，社区转向 Vite 或 Next.js
- 元框架：Next.js（Vercel，非 Meta）

这种 **unopinionated**（不给意见）的风格 = 自由 + 创新，但也 = **碎片化 + 选择困难**。每个新项目都要先开一轮「今年该用哪个状态库」的会。

### Vue：尤雨溪主导 + 官方全家桶 + Opinionated

Vue 由尤雨溪和核心团队主导，走 **opinionated**（有明确意见）路线，提供**官方全家桶**：

- 路由：Vue Router（官方）
- 状态：Pinia（官方推荐）
- 构建：**Vite**（尤雨溪本人作品，整个前端圈都在用，包括大量 React 项目）
- 测试：Vitest（官方，Vite 配套）
- 语言服务：Volar（官方）
- 元框架：Nuxt（官方生态紧密绑定）

好处是**开箱即用、风格统一、文档一致**；代价是**创新和多样性可能受限**，且生态规模总体小于 React。

> **核心洞察**：这是两种开源治理哲学。「给一个核心 + 让生态自由竞争」vs「给一整套协调的官方工具链」。没有对错，只有 trade-off——你的团队更看重「选择自由」还是「省心一致」。

## 第 9 章 2026 趋势：趋同与分歧（联网核实）

> 本章事实基于 2026/06 联网核实，非凭记忆。

这一章最值得讲，因为它能**反过来印证**前 8 章的哲学走向，还藏着 2026 年最容易被误读的一个点。

### React 2026：Compiler 稳定，但明确拒绝 Signals

**React Compiler** 已从 RC 进入稳定（v1.0）。它的核心能力是：**自动 memoize**——你不再需要手写 `useMemo`/`useCallback`，编译器自动分析哪些值需要缓存。

这件事的意义在于：它**消灭了 React 心智模型里最繁琐的部分**（手动 memo 的负担），而不是改变了响应式模型。

**关键事实：React 官方明确不采纳 Signals。** 核心团队有公开立场（如《Why React Should Not Adopt Signals》）。React 选择「**保持不可变 + diff 模型不变，用编译器优化 memoization**」，而不是引入细粒度响应式。Server Components、Actions、`use()` 等持续推进，但都建立在「重算 + 调度」这个地基上。

### Vue 2026：Vue 3.6 与 Vapor Mode

**Vue 3.6** 即将落地两大变化：

1. **Vapor Mode**：把模板**编译成直接的 DOM 操作**，**跳过虚拟 DOM**。这是把第 6 章「让编译器帮忙」推到极致——既然编译器能生成命令式代码，为什么还要中间的虚拟 DOM？
2. **reactivity 基于 alien-signals 重写**：大幅提升响应式系统的性能和内存占用。

需要诚实指出的代价：Vapor Mode 从 2023 年宣布到 2026 才落地，**进度偏慢**（社区有抱怨）；且存在生态兼容问题（如 Vuetify 依赖 `getCurrentInstance` 这类内部 API，与 Vapor 不兼容）。

### 趋同点 vs 分歧点（别混了）

这是本章的核心，也是修正常见误解的地方：

**趋同点 —— 「编译期优化」两边都在做。**
- Vue 一直在做（PatchFlag、静态提升，现在到 Vapor）；
- React 刚开始（React Compiler）。
- 编译器参与深度，是历史性的方向收敛。

**分歧点 —— 响应式模型依然根本对立，2026 没有收敛迹象。**
- 业界整体确实在向 **Signals** 收敛（Vue、Svelte、Solid、Angular 都已采用 signals 式细粒度响应式）；
- **但 React 是那个重要例外**——它拒绝 signals，转而用 Compiler 守住「不可变 + diff」的阵地。

所以网上常见的「2026 了，React 也终于要拥抱 signals 了吧」是**误读**。准确的表述是：

> **编译期优化：两边趋同。**
> **响应式模型：React 坚守 immutable+diff，其余主流框架走向 signals，分歧依旧。**

### 最容易被名字骗的一点：两个「Compiler」不是一回事

这是面试和博客里最常见的混淆。**Vue 的 Vapor（编译器）和 React Compiler 都叫 compiler，但解决完全不同的问题：**

| | Vue Vapor | React Compiler |
|---|---|---|
| 优化层面 | **结构级**：绕过虚拟 DOM，直接生成 DOM 操作 | **值级**：自动 memoize，减少无谓重算 |
| 是否抛弃 vdom | **是**（Vapor 组件不走 vdom） | **否**（仍是 vdom + diff） |
| 解决的根问题 | 「重算整棵树太贵」→ 干脆不重算，直接操作 | 「手动 memo 太烦」→ 自动算 |

把这两个「Compiler」混为一谈，就会得出「React 和 Vue 越来越像」的错误结论。**它们更像是在两条平行的赛道上各自冲刺，赛道本身（响应式模型）并没有合并。**

> **回扣根命题**：2026 的局面，恰恰是第 0 章那个根命题的当代证明——两个框架在编译优化上靠近了，但在「状态如何驱动 UI」这个根本问题上，依旧各自走自己的路。

## 第 10 章 试金石：5 个真实场景的并排剖析

理论讲够多，现在用**同一个问题、两种解法**来检验前面所有的论证。每个案例最后都回扣根命题。

### 试金石 1：大列表 + 频繁局部更新

**场景**：一个 10000 行的表格，每秒有若干行的某个字段被更新。

**React**：
- 列表必须**虚拟化**（react-window 等），否则渲染 10000 个 DOM 节点会卡；
- 每一行要用 `React.memo` 包裹，并用稳定的 `key`；
- 行组件内变更字段要 `setState`，但要注意**整行会重渲染**，依赖该行的子组件都要 memo；
- 数据层最好用外部 store + selector，避免 Context 导致全量重渲染。

**Vue**：
- 同样推荐虚拟化（vue-virtual-scroller）；
- 但**局部更新天然高效**：响应式是属性级细粒度的，某行某字段变了，**只有绑定该字段的那一个 DOM 节点**被更新，其他行零成本；
- 不需要到处 memo。

**回扣根命题**：「频繁局部更新」正是细粒度响应式的舒适区，是粗粒度「组件级重算 + diff」的痛点区。这不是 Vue 运气好，是根命题的必然。

### 试金石 2：复杂表单

**场景**：一个多字段、带联动校验的表单。

**React**：
- 典型做法是**受控组件**：每个输入 `value` 绑定 state，`onChange` 里 `setState`；
- 每次按键都触发组件重渲染（大表单要靠 `useDeferredValue`、拆组件、或 React Compiler 来优化）；
- 或者用 `react-hook-form` 这类**非受控**库绕开重渲染。

**Vue**：
- `v-model` 双向绑定，响应式自动处理，写起来就是声明 `ref` + `v-model`；
- 因为是细粒度响应式，**每次按键只更新那一个输入框的 DOM**，不会有「整个表单重渲染」的焦虑。

**回扣根命题**：表单场景下「直接改数据」的心智（Vue）比「产出新 state 让表单重渲染」（React）更贴合人的直觉。这背后还是可变响应源 vs 不可变快照。

### 试金石 3：跨层状态共享

**场景**：用户登录态要在很多不相关组件里用。

**React**：Context（小心全量重渲染）或 Redux/Zustand/Jotai。选型本身就是一门学问。

**Vue**：写一个响应式模块（或 Pinia store），到处 `import`。响应性是数据的属性，自然跨组件。

**回扣根命题**：第 5 章——「状态是渲染问题」还是「数据问题」，在这里直接体现为「共享状态要不要操心重渲染」。

### 试金石 4：异步、Suspense 与过渡

**场景**：点按钮触发一个慢请求，期间 UI 要保持可交互，加载完平滑切换。

**React**：
- **Suspense + Concurrent** 是 React 的杀手锏。`useTransition` 可以把一次昂贵的状态更新标为「低优先级过渡」，让用户输入不被阻塞；
- 这是 React「重算贵 → 用调度补救」路线集大成的体现，**Vue 目前没有等价的细粒度优先级调度**。

**Vue**：
- 也有 `<Suspense>` 和 `<Transition>`，体验上覆盖大部分场景；
- 但没有 React 那种「渲染可中断 + 优先级插队」的全套 Concurrent 能力。

**反向回扣**：这是**少数 React 在根命题上反而占优的场景**——正因为 React 把复杂性投到了运行时调度（Concurrent），它换来了「优先级 / 时间分片 / 可中断渲染」这组独特能力。Vue 的精准触发在「别做多余工作」上更强，但在「主动调度工作优先级」上较弱。**trade-off 是双向的。**

### 试金石 5：同一个 Todo 组件，并排写一遍

直接看「等价实现」最能暴露心智差异：

```tsx
// React —— 思考单位是「某一刻的 UI 快照」
function TodoList() {
  const [todos, setTodos] = useState<Todo[]>([])
  const [text, setText] = useState('')
  const remaining = useMemo(() => todos.filter(t => !t.done), [todos])
  function add() {
    setTodos([...todos, { text, done: false }])   // 产出新数组
    setText('')
  }
  return (
    <form onSubmit={e => { e.preventDefault(); add() }}>
      <input value={text} onChange={e => setText(e.target.value)} />
      <span>剩余 {remaining} 项</span>
    </form>
  )
}
```

```vue
<!-- Vue —— 思考单位是「数据与响应关系」 -->
<script setup lang="ts">
import { ref, computed } from 'vue'
const todos = ref<Todo[]>([])
const text = ref('')
const remaining = computed(() => todos.value.filter(t => !t.done))
function add() {
  todos.value.push({ text: text.value, done: false })   // 直接改
  text.value = ''
}
}
</script>
<template>
  <form @submit.prevent="add">
    <input v-model="text" />
    <span>剩余 {{ remaining }} 项</span>
  </form>
</template>
```

观察对比：

- React 版**多出来** `useMemo`、`onChange` 受控写法、`[...todos]` 不可变更新——每一处都是「不可变快照 + 重算」模型的注脚；
- Vue 版**没有**这些：`computed` 自动追踪依赖、`v-model` 自动双向、`push` 直接改。
- React 版**少**了什么？它没有响应式的「魔法」，一切对 JS 开发者都透明可预测——这恰恰是 React 哲学的卖点。

**回扣根命题**：同一份功能，React 版处处写着「不要改，要替换；重算会自然发生」，Vue 版处处写着「改就是了，框架盯着」。**代码的形态，就是根命题的可读投影。**

## 第 11 章 选型决策框架

不站队，给框架。选型本质是在一组 trade-off 里找最匹配你场景的解。

### 决策矩阵

| 维度 | 倾向 React | 倾向 Vue |
|---|---|---|
| 团队背景 | 团队函数式思维强、习惯不可变模型 | 团队偏好直观的「改数据」心智 |
| 生态需求 | 需要超大生态、大量第三方库、招人容易 | 需要开箱即用的官方全家桶、风格统一 |
| 项目特征 | 高度异步/并发、复杂调度、SSR/RSC 重度 | 大量表单、大量频繁局部更新、内容管理类 |
| 长期维护 | 愿意为选型自治付出成本 | 想要官方背书的统一技术栈 |
| 类型体验 | 已有成熟 React+TS 模式 | 想要编译器深度参与类型（Volar、defineProps） |

### 几条经过验证的经验

1. **别用「哪个更流行」做决策**。流行度是招聘市场的指标，不是技术匹配度的指标。
2. **警惕「XX 更快」的笼统结论**。性能取决于场景（见试金石 1 和 4），两边在各自舒适区都快。
3. **2026 年的新变量：React Compiler 与 Vapor Mode**。前者降低 React 的 memo 心智负担，后者提升 Vue 的渲染性能——如果你的项目时间线在未来一年，把这两个成熟度纳入考量。
4. **治理偏好往往比技术差异更决定长期体验**。一个爱「自己挑工具」的团队会嫌 Vue 全家桶束缚；一个想「专注业务」的团队会嫌 React 选型烦。

### 一句话总结

> **React 是「给懂函数式的人的最大灵活度」；Vue 是「给想专注业务的人的最短路径」。**

## 尾声

回到第 0 章那张表。整篇文章其实只在反复证明一件事：

> **Vue 和 React 的所有差异，都可以回溯到「状态是不可变快照，还是可变响应源」这一个根命题。**

- 闭包陷阱、Hooks 规则、必须 memo——都是「快照 + 重算 + 手动依赖」的代价。
- 响应式坑（解构丢响应、要理解追踪时机）、Vapor 兼容性——都是「可变 + 自动追踪 + 编译器参与」的代价。
- 2026 年两个 Compiler 名字相似但解不同题——恰恰证明根命题依旧分叉，没有合并。

**不存在谁更好，只存在你愿意承担哪种代价。** 理解了根命题，你就不再需要背 API 对照表——任何一个新 API 出现，你都能瞬间把它归位到那张表里，判断它是本质演进还是表面文章。

这，才是「深刻对比」的意义。
