# HTML 增强表达方法论

## 核心理念

不是把 Markdown "转换"为 HTML，而是**重新审视每一类信息，用 HTML/SVG/交互性找到比纯文本更好的表达方式**。

原则：
- Markdown 是信息源，HTML 是表达层——信息不丢失，但表达方式升级
- 每种内容类型有自己的最佳 HTML 呈现形式
- 优先用 SVG 替代 ASCII 图，用交互性替代平铺叙述，用视觉层级替代格式标记

## 信息不丢失原则

| 原则 | 说明 |
|------|------|
| 全文保留 | 每段 prose 分析逐字进入 HTML，不做删改 |
| 数据完整 | 每个表格的所有单元格都出现在 HTML 中（即便被重新排版） |
| 标注保留 | 所有 `[推测]` 标记在 HTML 中有对应可视化标注 |
| 链接可达 | 所有交叉引用在 HTML 中都能点击到达目标章节 |
| 推演完整 | 每个反事实推演的"假设→后果→结论"链条完整呈现 |

## 内容类型 → HTML 增强策略

报告中的信息分为 8 种内容类型，每种有独立的增强方案：

### 类型 1：ASCII 架构图 → 内联 SVG

Markdown 中的 box-drawing 字符图表达力有限、对齐脆弱、无法交互。全部替换为 SVG。

| 10:系统交叉 | 7 个系统的强弱耦合网络 | 节点连线图，强耦合实线、弱耦合虚线，hover 高亮关联边 |
| 01:核心循环 | 宏循环流程（探索→地下城→物品→新区域） | 水平循环箭头图，每个节点可点击跳转到对应章节 |
| 12:难度与心流 | 全流程阶梯难度曲线 | SVG 折线图，x 轴为 13 个地下城，y 轴为难度，hover 显示具体数值 |

| 来源 | 图内容 | SVG 方案 |
|------|--------|---------|
| 03:地下城设计 | Boss 学习循环（首次遭遇→观察→识别→尝试→击倒） | 5 步循环箭头图 |

**SVG 技术规范：**
- viewBox 固定，不设固定宽高（响应式缩放）
- 配色与页面 CSS 一致
- 文字用 `<text>` 元素（可选中、可搜索）
- 简单 hover 效果用纯 CSS（`:hover` 改变 fill/stroke/opacity）
- 需要点击交互的（展开/折叠/切换）用少量内联 JS
- JS 限制：仅用于 SVG 内部的 `classList.toggle` 和表格的行列高亮，不超过每个页面 50 行

### 类型 2：数据表格 → 增强表格

Markdown 表格是纯文本网格。HTML 表格可以有视觉层级、交替行色、列高亮。

**增强方案：**

| 表格 | 来源 | 增强方式 |
|------|------|---------|
| 13 个地下城完整数据 | 03 | 粘性表头、按"所在世界"分色、Boss 名链接到 Boss 详情表 |
| Boss 攻击模式/弱点 | 03 | Boss 名用彩色标签、弱点列用图标标注对应道具 |
| 物品-用途对照 | 04 | 三色标签（解谜/探索/战斗）标注每行用途类型 |
| 谜题类型学 | 06 | "首次出现地下城"列带超链接 |
| 交互矩阵（物品×系统） | 09 | 行/列 hover 高亮交叉格，核心交互用深色、偶发用浅色 |
| 系统交叉矩阵（8×8） | 10 | 强耦合格红色、弱耦合格蓝色，hover 显示具体表现 |
| 物品协同度排行 | 09 | 柱状进度条可视化"总交互数"列 |
| 地下城难度维度评分 | 12 | 每格用 ★★★ 数量 + 颜色深浅双重编码 |
| 系列范式清单 | 13 | 时间线样式，左侧年份、右侧范式名 |

**通用表格样式：**
- 粘性表头（`position: sticky`）
- 交替行底色
- 第一列加粗（通常是名称列）
- 横向可滚动容器（窄屏）

### 类型 3：反事实推演 → 可折叠推理卡

每篇报告的"反事实推演"章节包含多个假设，每个假设有"假设→后果→结论"三段结构。

**增强方式：**
- 每个假设包裹为 `<details>` 可折叠卡片
- 卡片标题（`<summary>`）显示假设内容（如"假设一：如果去掉'物品即钥匙'"），始终可见
- 展开后显示后果列表 + 结论
- 卡片左侧有 4px 红色色条，表示"如果移除 X 会怎样"的警示感
- **默认展开第一个假设，其余折叠**——让读者看到交互方式，但不被全部内容压到

**视觉设计：**
```
┌─ ━━━ 假设：如果去掉"物品即钥匙"的机制 ──────── [点击展开] ─┐
│                                                                │
│  后果：                                                        │
│  • 表世界探索失去核心驱动力                                    │
│  • 地下城之间变成纯线性排列                                    │
│                                                                │
│  结论：物品即钥匙是核心循环的脊柱                              │
└────────────────────────────────────────────────────────────────┘
```

### 类型 4：可迁移经验 → 独立经验卡

每篇报告末尾的"可迁移经验"是一组独立的设计原则。在 HTML 中将每条经验做成**独立的卡片组件**。

**增强方式：**
- 每条经验是一张浮动卡片（圆角、浅背景、左侧色条）
- 卡片头部是加粗的原则名称
- 卡片正文是操作步骤或解释
- 同一报告的所有经验卡排列成网格（大屏 2 列，小屏单列）
- 卡片右下角显示来源报告编号（点击跳转回对应分析章节）

### 类型 5：[推测] 标注 → 旁注标记

**增强方式：**
- 行内 `[推测]` 变为小圆角标签（浅橙底 + 深橙字，字号小于正文）
- hover 时显示 tooltip：`"以下内容为基于约束和目标的推导，非已确认事实"`
- 不打断阅读流，但视觉上可识别

### 类型 6：交叉引用 → 导航链接 + 上下文提示

Markdown 中的 `→ 参见 XX_标题.md` 是扁平文本链接。

**增强方式：**
- 链接样式带 `→` 前缀图标，用不同颜色（蓝紫系）区分于普通链接
- hover 时 CSS 显示一个 tooltip，内容为目标报告的核心问题（一句话）
- 点击直接跳转，跨页面跳转带锚点定位

**数据准备**：需要为每篇报告提取一句核心问题摘要（可直接从各报告的"核心问题"章节第一句提取），作为 tooltip 内容，存储在链接的 `data-summary` 属性中。

### 类型 7：流程/步骤叙述 → 可视化步骤条

报告中的设计过程推导、教学链等有序步骤（用 `1. 2. 3.` 或 `→` 链表达），转为可视化步骤条。

**适用位置：**

| 来源 | 步骤内容 |
|------|---------|
| 04:进度系统 | 设计过程推导的 6 步路径 |
| 06:谜题设计 | 无文字教学三步法则 |
| 09:元素协同 | 物理行为抽象法的 4 步操作 |
| 10:系统交叉 | 先骨架后血肉的 4 步流程 |
| 13:设计全景图 | 设计过程宏观还原的 7 个阶段 |

**增强方式：**
- 左侧竖线连接的圆点步骤条
- 每步有编号圆点 + 标题 + 正文
- 当前步骤的圆点填充色，其余空心
- 纯 CSS 实现，不需要 JS

### 类型 8：补充材料 → 页底折叠区

每篇报告的"补充材料"（对比参考、数据来源、交叉引用索引）在 HTML 中默认折叠。

**增强方式：**
- 整个"补充材料"章节用 `<details>` 包裹
- 标题栏显示"补充材料" + 展开箭头
- 展开后显示完整内容
- 交叉引用列表改为带图标的链接列表

## 图片策略

### 来源

Zelda Wiki (zeldawiki.wiki) 和 Zelda Dungeon (zeldadungeon.net)。

### 原则

不设固定配图数量。每篇报告根据内容需要引入图片——如果某个段落讨论了具体的地下城、Boss、物品、场景，而 Wiki 上有对应的截图/地图/图标能帮助读者直观理解，就引入。

**引入判断标准：**
- 该段落描述了一个**视觉上可识别**的游戏元素（特定物品、特定场景、特定 Boss）
- 图片能传递**纯文字难以传达**的信息（如地下城的空间结构、双世界的视觉对比）
- 该图片在 Wiki 上**确实存在且质量可接受**

**不引入的情况：**
- 段落讨论的是抽象设计原则，没有具体游戏元素
- 图片只是装饰性，不增加理解
- 找不到高质量图片

### 存储

- 下载到 `html/images/`
- 命名：`{描述}.png`（无需编号前缀，用有意义的英文名）
- 单张 ≤ 400KB
- 用 `<figure>` + `<figcaption>` 包裹
- 同一图片可在多篇报告中复用（如 Hookshot 截图在 03/04/09 中都可能用到）

## 执行流程

### 阶段一：骨架搭建

1. 创建 `html/` 目录结构、`style.css` 基础样式、通用页面模板
2. 实现 `index.html` 首页
3. 实现 sideber 导航组件（每页复用）

### 阶段二：逐篇手工增强（01 → 13）

每篇报告的处理步骤：

1. **文本层**：将 Markdown 正文逐段放入 `<main>` 内容区，保留所有文字
2. **SVG 层**：识别该篇中的 ASCII 图，制作对应的内联 SVG 替代
3. **表格层**：识别该篇中的数据表，应用增强表格样式和交互
4. **结构层**：
   - 反事实推演 → `<details>` 卡片
   - 可迁移经验 → 独立经验卡
   - 补充材料 → `<details>` 折叠区
   - 步骤叙述 → 步骤条
5. **标注层**：处理 `[推测]` 标记、交叉引用链接
6. **图片层**：从 Wiki 下载该篇需要的截图，插入 `<figure>`

### 阶段三：全局连通

1. 交叉引用链接全部指向正确的 HTML 文件和锚点
2. 侧边栏导航在每页正确高亮当前报告
3. 面包屑正确显示

### 阶段四：验证

执行质量检查清单。

### 自动化 vs 手工的边界

| 步骤 | 方式 | 原因 |
|------|------|------|
| Markdown → 基础 HTML | Python 脚本 | 批量、机械 |
| 交叉引用链接替换 | Python 脚本（正则） | 有固定模式 |
| [推测] 标注处理 | Python 脚本 | 有固定模式 |
| SVG 制作 | 手工 | 需要设计判断 |
| 表格增强（分色、图标） | 手工 | 需要逐表判断 |
| 可折叠/经验卡结构 | Python 生成骨架 + 手工调优 | 结构有规律但需微调 |
| 图片选取与插入 | 手工 | 需要判断相关性 |
| CSS 样式 | 手工编写 style.css | 设计工作 |
| 内联 JS（hover 交互） | 手工 | 按需添加 |

## 质量检查

| 检查项 | 验证方式 |
|--------|---------|
| 信息完整性 | 逐段对比 md 源文件，确认无遗漏段落 |
| SVG 渲染 | 每个 SVG 在 Chrome/Firefox 正常显示、hover 正常 |
| 表格数据 | 对比源表格，确认每个单元格都存在 |
| 交叉引用 | 每个链接点击可到达目标页面/锚点 |
| 可折叠组件 | 每个 details/summary 可正常展开折叠 |
| 图片 | 每个 img 标签有对应本地文件 |
| 离线 | 断网后全部页面/图片/SVG 可用 |
| 响应式 | 1920px / 1024px / 768px / 375px 检查 |
